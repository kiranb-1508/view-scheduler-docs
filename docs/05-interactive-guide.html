How the View Scheduler works

One job refreshes a view on a schedule. An upstream table may not have refreshed yet. The refresh still runs and publishes stale data. Nothing errors. Nobody is told. This guide shows how the tool makes that failure loud, step by step. It marks every important design decision. It ends with the open findings that wait for your approval.

1 · The problem, in one sentence

The whole point

A confident wrong answer, not an error. The view refresh succeeds. The data is old. No log line says so. Every requirement below exists to turn that silence into a loud answer.

Two questions need two different tools. This is the core design split.

Tool 1 · advisory

advise("sales.gold.customer_360")

Question: When can this view usually run, with every upstream job finished?

Method: Read 30 days of history. Predict a safe time and an earlier time.

Nature: A prediction. It does not check today. Pair it with the gate.

Tool 2 · the gate

can_refresh("sales.gold.v_orders")

Question: Can this view refresh right now? Is every dependency fresh?

Method: Walk every dependency. Check its last real write against its own rolling window.

Nature: The product. It decides. It never refreshes. READY only when everything is fresh.

Boundary rule

Read-only, decide-only. The package never writes, alters, optimizes, or refreshes anything. All I/O is metadata and history reads. If a change would write to your data, it is out.

2 · Follow one view, end to end

Click a step. The panel shows what happens and why it exists.

You call the gate

One line inside a Databricks job. result = can_refresh("sales.gold.v_orders"). The warehouse ID comes from the WAREHOUSE_ID environment variable, so no configuration is needed in the common case.

You may pass one view or a list. A list gives one verdict per view and one overall verdict.

gate.py → can_refresh()

The workspace seam opens the door

Every external call goes through one small object: Workspace. It wraps the Databricks SDK and the SQL Statement API.

Why one seam? The walk and the gate run offline in tests with no network and no credentials. The tests inject a fake Workspace. A second I/O path would break that.

client.py → Workspace · get_table() · sql()

The walk finds the physical tables

The gate asks Unity Catalog for the view. It reads view_dependencies. The name sits one level down: dependency["table"]["table_full_name"].

Views inside views are followed. The walk stops at physical tables, materialized views, and streaming tables. A cycle is a blocker. A depth cap of 60 stops runaway graphs. Every dependency ends in one list with an ok flag — measured tables, cycles, unreadable objects, function notes. One list, not three channels.

walker.py → walk()

Each table tells its last write

For a table or streaming table: DESCRIBE HISTORY through the SQL Statement API. Timestamps are read as epochs, not rendered strings — a rendered timestamp depends on the warehouse session time zone, which the tool does not control.

A materialized view rejects DESCRIBE HISTORY. Its completed refreshes come from the pipeline event log instead. A streaming table is a Delta table and answers DESCRIBE HISTORY — its refreshes appear as STREAMING UPDATE commits.

client.py → read_delta_history() · read_mv_refreshes() · read_latest_commit()

Each commit gets a class

The classifier reads the operation name and the mode together. A plain WRITE plus mode Overwrite is a full replace. WRITE plus Append is incremental. OPTIMIZE, VACUUM, DELETE and friends are maintenance and never count.

A zero-row write still counts. A full replace that produced no rows still ran. So did a zero-row append. The pipeline ran that day; the data is as fresh as it gets.

history.py → classify() · qualifying()

The window decides

Each table is checked against its own schedule. A daily table gets fresh_hours, default 24. A table that runs less often gets a wider window: the longest gap between its run weekdays, plus one, times fresh_hours. A write exactly at the edge is fresh. One second past is stale.

A write dated after the reference time is ignored. A clock-skewed future commit must not make a stale table look fresh.

gate.py → _history_summary() · _verdict_for() · config.py → fresh_hours

The report speaks plainly

One block per view. Every dependency gets a line, with its age — not only the blockers. Every blocker names the dependency and the view that needs it. The report ends with one actionable line: what to refresh, and for whom.

Anything unreadable blocks the view. The gate fails closed. It never raises for a dependency problem.

gate.py → GateResult.render()

Your job acts on the answer

result = can_refresh("sales.gold.v_orders")
if result.ready:
    ...run the refresh...
else:
    print(result)   # says exactly what to fix

The gate decided. The gate did not refresh. That split is deliberate and permanent.

The decision ladder

Every dependency falls down this ladder. The first matching rung decides.

What is it? A view → recurse. A function → note. Anything unreadable → block.shape
Is it a streaming table? Read its Delta history like a table. A scheduled one is stale between runs.history
Is it a materialized view? Read its pipeline event log for a completed refresh.event log
Is there a qualifying write? A write that ran — even with zero rows. Maintenance never counts.classify
Is it inside its own window? A daily table gets fresh_hours; a trusted weekly-ish table gets a wider one. And not dated after the reference time?fresh
Any rung fails or errors → the dependency blocks the view, with a plain reason.stale / blocked
All dependencies fresh → READY. The job may refresh.ready

5 · The advisory tool — how a safe time appears

  
The advisory tool reads the last 30 days. For each dependency it keeps the first qualifying
  write of each local day. That is the day's finish time. Then it intersects the days.

  

    

      1 · per day
      
Each table's finish time

      
For each local day, take the first commit that is a real refresh. OPTIMIZE at 09:00 does not count;
      a zero-row append at 04:00 does.

    

    

      2 · intersect
      
Days when everything finished

      
Keep only the days where every dependency has a finish time. One missing table removes the day.

    

    

      3 · choose
      
Safe and earlier

      
safe = the latest finish time seen on the all-clear days, plus the buffer (15 min).
      earlier = the typical day: the median finish time of the all-clear days, plus the same buffer. A slower day still finishes after it.

    

  

  

    Open finding B1 — read before you rely on it
    
The tool assumes the first commit of a day means "finished loading". A table that writes a
    small early commit and the real load later gets a safe time at the wrong moment. The only guard is a
    "continuous" flag that needs 6+ commits a day. This matters. See finding B1.

  

  
The buffer and midnight. A 23:50 finish plus a 15-minute buffer crosses midnight.
  The report marks it (+1 day) and warns. Nothing is silently wrapped.







  
6 · The design decisions that matter

  
Open each card. The pattern is the same everywhere: decision → why → what breaks without it.


  
D1Read-only. Decide-only. Never refresh.
  

    
The package answers one question and stops. The calling job acts.

    
Why: A tool that can refresh can also refresh wrongly. Splitting the decision from the
    action keeps the blast radius at zero. A wrong decision is a log line; a wrong write is an incident.

    
Without it: the gate could trigger a refresh loop, or mask the very staleness it reports.

  


  
D2Fail closed: a false BLOCK beats a false READY.
  

    
Unreadable, missing, no history, cycle, depth cap, view with no dependencies — each one blocks.

    
Why: The product exists to stop a confident wrong answer. "I could not check" must never
    read as "it is fine".

    
Without it: a permission error on one table turns into a silent READY. That is the original
    bug in a new costume.

  


  
D3A rolling window in hours, not a calendar day.
  

    
Default 24 hours. One value per call. Overridable with fresh_hours.

    
Why: "Ran today" is true at 00:01 for a table that ran at 00:00 yesterday. A rolling
    window matches the real question: "did it write recently enough?".

    
Without it: a stale table looks fresh right after midnight.

  


  
D4Classify by mode, not by operation name.
  

    
The commonest Delta operation is plain WRITE. Only operationParameters.mode
    says whether it replaced or appended a table.

    
Why: Classify by name alone and most tables read as dormant — a confident wrong answer,
    not an error. This bug shipped once.

  


  
D5A zero-row write still counts as a refresh.
  

    
A full replace that produced no rows still ran. So did a zero-row append.

    
Why: The question is "did the pipeline run?", not "did it produce data?". A quiet day is
    not a missed day.

  


  
D6Read time as epochs, never as rendered strings.
  

    
SELECT unix_timestamp(timestamp) returns the instant. A rendered TIMESTAMP string depends on the
    warehouse session time zone, which this tool does not control.

    
Why: Stamping a naive value with the config zone is wrong by the UTC offset. This bug
    shipped once too.

  


  
D7Quote every name part. Encode every URL path.
  

    
Backtick each dot-separated part. Double an inner backtick. Percent-encode the metadata path.

    
Why: A hyphenated name is subtraction unless quoted. An unquoted name is an injection
    surface.

  


  
D8Read every result chunk. Refuse a truncated result.
  

    
The SQL Statement API paginates. The reader follows the chunks to the end. A truncated manifest raises.

    
Why: Using only the first page hides older commits. The gate would call a fresh table
    stale — or worse, date it wrongly.

  


  
D9A materialized view is read from its pipeline event log.
  

    
An MV rejects DESCRIBE HISTORY. Its completed refreshes live in
    event_log(TABLE(mv)) as update_progress events with state COMPLETED.

    
Open edge (A2): that event is pipeline-scoped. An update that skipped this MV still counts today.

  


  
D10A streaming table is checked from its history — v0.4.0 reversal.
  

    
Until v0.3.0 the rule was "a streaming table is always fresh". Live data disproved it: a scheduled streaming
    table went 24 days without a single commit. The gate called it fresh through all of them — a false READY.

    
Now: a streaming table is a Delta table. Read its history. Apply the same window. A scheduled
    one is stale between runs; a paused one is stale the whole time it is paused.

    
Why it is safe: a continuous streaming table that ingests writes commits often and stays
    fresh naturally. See the case study below.

  


  
D11A function dependency is a note, not a blocker.
  

    
A SQL UDF usually has no refresh to wait for, so it does not block.

    
Open edge (A1): a UDF with READS SQL DATA, or a table-valued function, can read a
    physical table. Unity Catalog records only the function. The gate then answers READY without measuring that
    table. This is the same shape as the "always fresh" bug. It needs your decision.

  


  
D12The cycle guard tracks in-progress and resolved names apart.
  

    
A single "seen" set fails open: nothing left to check, and all(()) is True — a
    cycle reported READY. The guard tests a name as in-progress (a back edge = a cycle) and as resolved.

    
Why: the empty-set trap is easy to reintroduce. It is tested.

  


  
D13The walk stops at tables, materialized views, and streaming tables.
  

    
Recurse views only. Everything else is a leaf with its own freshness check.

    
Open edge (A3): the API also sets view_dependencies for MV and streaming
    types. The walk does not follow them. An MV refreshed on schedule from a stale source reads fresh today.
    Deliberate — but now a measured blind spot.

  


  
D14One list of dependencies per view.
  

    
Measured tables, cycles, unreadable objects, and function notes all become one Dependency with
    an ok flag. The verdict is all(d.ok).

    
Why: one channel means one place to check, one report format, and no path where a
    blocker gets lost between lists. Three channels drift apart.

  


  
D15Every blocker names the dependency and the view that needs it.
  

    
The report ends with: c.s.t_old   (needed by c.s.v).

    
Why: at 3am, "something is stale" is useless. The fix must be copy-pasteable.

  


  
D16Four settings only. Ask before a fifth.
  

    
days_history (30), buffer_min (15), timezone (Asia/Kolkata),
    fresh_hours (24). That is the whole surface.

    
Why: every new setting doubles the number of behaviours to test and document. The v0.4.0
    streaming-table change added none. It needed none.

  


  
D17Bump the version when behaviour changes.
  

    
The pre-gate wheel and the gate wheel were both 0.1.0 once. Pinning was impossible.
    The v0.4.0 change to streaming tables follows this rule.

  


  
D18All tests run offline. Pinned clock. Golden report text.
  

    
No network, no warehouse, no Spark, no credentials. A fake Workspace injects history.
    Every test passes now=, so the rolling window is deterministic. The report text is pinned
    byte-for-byte by a golden test.

    
Open gap (E1): the tests never exercise the real SQL seam — pagination, chunks, the
    timeout. See the findings.

  


  
D19Plain words in every user-visible string.
  

    
The two times are called safe and earlier. The columns are
    RUNS / USUAL / LATEST / DAYS / MISSED. Never "tighter", "all-clear", or jargon like "window"
    without the number.

  







  
7 · Case study: the streaming table that was not always fresh

  
This is the clearest example of the class of bug this project hunts. It is now fixed. The proof comes from
  your own live schema, read-only.


  

    
  


  

    

      Before · v0.3.0
      
Fresh by definition

      
The gate never read the table's history. It answered fresh on every one of the 24 gap days.

      
A view that depended on this table would refresh with day-old (or month-old) data, confidently.

    

    

      After · v0.4.0
      
Checked from history

      
The gate reads STREAMING UPDATE commits like any write. The same 24h window applies.

      
During the gap the verdict is BLOCKED after the first 24 hours, until the writes resume.
      No new setting. No new I/O path. The classifier already knew the operation.

    

  

  

    Why this matters beyond one table
    
The bug was not a crash. It was a design rule — "always fresh" — that sounded safe and was wrong for a
    subclass: the scheduled streaming table. Every open finding below is checked for this same shape.

  







  
8 · War stories — bugs already found and fixed

  
Each one shipped once. Each one now has a test. They teach the traps.

  
A cycle reported READY
  

    
Deduplicating on one "seen" set left nothing to check, and all(()) is True.
    The empty set passed the test. Now in-progress and resolved names are tracked apart, and a cycle blocks.

  

  
Naive UTC stamped with the config zone
  

    
A notebook returns a naive UTC datetime. The code stamped it with the config zone — wrong by the UTC
    offset. Fix: read epochs. An epoch is the same instant everywhere.

  

  
Only the first result page was read
  

    
The SQL Statement API paginates. The first version read page one and stopped — older commits invisible.
    Fix: follow every chunk and refuse a truncated result.

  

  
A future-dated commit passed as fresh
  

    
A clock-skewed commit dated after "now" made a stale table look fresh. Fix: ignore writes after the
    reference time.

  

  
Unquoted names in SQL and URLs
  

    
A hyphenated name becomes subtraction. An unquoted name is an injection surface. Fix: quote every part,
    encode the path.

  

  
A hand-written README example was wrong in three ways
  

    
Nobody noticed for weeks. Fix: generate the sample output from the code, and pin the report with a
    golden test.

  

  
Docs that said the gate was never built
  

    
The docs pointed the reader at themselves while describing a missing tool. Fix: docs track the code.
    The runtime gate ships as can_refresh.

  







  
9 · Open findings — proposed changes, waiting for approval

  
A deep audit (five independent passes over the gate, the walk, the I/O seam, the advisory tool, and the
  Databricks docs) found these. None is fixed yet. Filter by type.

  

    
    
    
    
    
    
  

  

    

      
IDFindingTypeProposed fix

      
        
A1
          A function dependency hides the tables it reads. A SQL UDF with READS SQL DATA, or a table-valued function, can read a physical table. UC records only the function. The gate answers READY without measuring that table. A function-only view is READY with nothing measured.
          false READY needs decision
          Make an unresolvable function a blocker, or follow routine_dependencies where possible. Reverses a settled decision — owner call.

        
A2
          The MV event log is pipeline-scoped, not MV-scoped. A shared pipeline can complete an update that skipped this MV ("select tables for refresh"). The gate reads COMPLETED and calls the MV fresh.
          false READY
          Count only this object's own completed update; verify against a live shared pipeline.

        
A3
          The walk stops at MVs and streaming tables. The API sets view_dependencies for those types too. An MV refreshed from a stale source reads fresh today.
          false READY needs decision
          Follow MV/ST dependencies one level, or record the blind spot as accepted. Owner call.

        
A4
          A failed or canceled streaming refresh can leave committed batches behind. DESCRIBE HISTORY shows the commit, not the failure. A partly-failed refresh reads fresh.
          false READY
          Cross-check the pipeline event log for a COMPLETED update covering this table.

        
A5
          A naive now in a DST zone picks the wrong offset on the ambiguous hour.
          false READY
          Reject a naive now, or document the requirement. Low blast radius; the default clock is correct.

        
B1
          The advisory tool treats the first commit of a day as "finished loading". A table with a small early commit and a later real load (or 2–5 batches a day) gets a safe time at the wrong moment. The rig cannot catch it — the oracle shares the assumption.
          wrong time
          Detect multi-write tables and say so, or use the last qualifying commit of the day for the safe time.

        
B2
          An unreadable dependency is dropped from the intersection, but the headline still says "every job had finished". A late, unreadable job cannot push the safe time later.
          wrong time
          Refuse to print a safe time when any dependency is unreadable.

        
B3
          Clock-time sort across midnight inverts safe and earlier: a 00:05 finish sorts before a 23:55 finish.
          wrong time
          Sort by full datetime, then compare clock times only for display.

        
B4
          buffer_min is never validated. --buffer -30 shifts the safe time earlier than anything observed. --days 0 crashes the CLI with a raw traceback.
          wrong time crash
          Validate both settings at construction time, inside the CLI error handling.

        
C1
          Shallow clones (MANAGED_SHALLOW_CLONE, EXTERNAL_SHALLOW_CLONE) are real Delta tables with history, but they are not in the gating set. A view on a fresh clone blocks.
          false BLOCK
          Add both types to the gating set. Verify history on a live clone.

        
C2
          FOREIGN, METRIC_VIEW, ONLINE, and connection/credential dependency kinds fall to "unrecognised" and block.
          false BLOCK
          Give each kind an explicit rule: check, note, or block with a specific reason.

        
C3
          A slow history read or a cold serverless start cancels against the 50s timeout. A history over 25 MiB aborts. A fresh, busy table blocks — every call.
          false BLOCK
          Use on_wait_timeout=CONTINUE with polling, and bound the history read.

        
C4
          Managed Iceberg tables gate, but their history operations do not match the Delta classifier. Unknown operations do not count.
          false BLOCK
          Classify Iceberg operations, or name the unknown ones in the gate report.

        
C5
          The gate reports "no qualifying refresh in history" even when the truth is "wrote with an operation we do not know". The advisory tool names unknown operations; the gate does not.
          false BLOCK
          Carry the unknown-operation names into the gate's detail text.

        
C6
          The MV fallback fires on one exact error string; a JSON-path drift in the event log returns "no qualifying refresh" instead of a read error.
          false BLOCK
          Broaden the fallback trigger; distinguish "empty event log" from "query drifted".

        
D1
          tools/classify_real.py imports _read from run.py. That symbol no longer exists. The committed tool is broken.
          crash
          Update the import to the current API.

        
D2
          One malformed history row (NULL timestamp, short row) poisons the whole table read. The reason shown is a read failure, not the real state.
          crash
          Skip a malformed row, or fail the table with a specific reason.

        
E1
          The real Workspace.sql seam has zero offline tests. Pagination, chunks, the truncation guard, the manifest, the timeout — the code where C3 and D2 live — never runs in the suite.
          tests
          Add offline tests with a fake SDK transport for the seam.

        
E2
          The fake Workspace in tests routes SQL by the substring event_log. A table named like that is misrouted in tests.
          tests
          Match the real statement shape, not a substring.

10 · Glossary and file map

  

    

      
Terms in one line each

      
    
        
  • View — a saved query. It stores no data; its answer is computed when read.
    • 
        
  • Materialized view (MV) — a view whose result is stored and refreshed by a pipeline.
    • 
        
  • Streaming table — a table fed by a streaming pipeline. It can run continuously or on a schedule.
    • 
        
  • Delta table — a table with a commit history. DESCRIBE HISTORY lists every write.
    • 
        
  • Commit — one write to a table: a version, a time, an operation, a mode.
    • 
        
  • Event log — a pipeline's own record of updates. An MV's refreshes live here.
    • 
        
  • Qualifying write — a write that ran and counts as a refresh. Zero rows is fine. OPTIMIZE is not.
    • 
        
  • Rolling window — "within the last N hours", checked against the exact moment. Not a calendar day.
    • 
        
  • Fail closed — when in doubt, BLOCK. A false BLOCK beats a false READY.
    • 
        
  • Epoch — seconds since 1970 UTC. The same instant in every time zone.
    • 
        
  • Golden test — a test that pins exact output text.
    •
