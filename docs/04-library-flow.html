Design record

From view name to schedule time

This page records the original design of the library, with the shipped rules marked. The current, verified flow is 08 · One spine, two answers. Blue boxes do I/O, gray boxes do pure computation, and red branches become visible warnings instead of disappearing.

Superseded

Read this as history, not as the current flow. Since this design the library gained a runtime gate, a Spark read path, gated streaming tables, and a rule that a zero-row write counts.

Important boundary

The library is read-only. It does not wait for dependencies, write tables, parse SQL, or modify the workspace. It answers from metadata and table history only.

1. The complete flow

The main path is vertical. Side branches are not failures of the whole run: they become named evidence or warnings in the final report. A streaming table is a gating table and is read like any other table.

3. The important decisions in plain language

Dependency discovery

Views are opened recursively through the UC API. Physical tables become inputs to history analysis. Unknown or unreadable dependencies remain visible in skipped.

Refresh classification

WRITE is not enough. The code checks operationParameters.mode. Full replacements qualify even when they write zero rows.

The runtime gate

can_refresh checks every dependency's latest write before the refresh runs, and fails closed. The advisor never waits: it suggests a time from history, while safe and earlier show the cost of choosing an earlier time.

4. How the outlier case appears

A table normally finishes at 07:00 but finishes at 08:00 once:

  • safe: 08:15, because it covers the observed worst day;
  • earlier: approximately 07:15, because it is the median normal day, not the observed worst day;
  • evidence: the report names the date, table, usual time, worst time, and the one-day risk.

The library does not silently delete the 08:00 incident. It lets the operator decide whether that incident should permanently influence the schedule.
