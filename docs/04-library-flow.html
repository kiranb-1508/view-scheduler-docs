Visual implementation guide

From view name to schedule time

This is the complete flow of the proposed library. Read it from top to bottom. Blue boxes do I/O, gray boxes do pure computation, and red branches become visible warnings instead of disappearing.

Important boundary

The library is read-only. It does not wait for dependencies, write tables, parse SQL, or modify the workspace. It answers from metadata and table history only.

1. The complete flow

The main path is vertical. Side branches are not failures of the whole run: they become named evidence or warnings in the final report.

3. The important decisions in plain language

Dependency discovery

Views are opened recursively through the UC API. Physical tables become inputs to history analysis. Unknown or unreadable dependencies remain visible in skipped.

Refresh classification

WRITE is not enough. The code checks operationParameters.mode. Full replacements qualify even when they write zero rows.

No runtime gate

The library never waits. A missed refresh becomes evidence, while safe and sooner show the cost of choosing an earlier time.

4. How the outlier case appears

A table normally finishes at 07:00 but finishes at 08:00 once:

  • safe: 08:15, because it covers the observed worst day;
  • sooner: approximately 07:15, because it excludes the single worst day;
  • evidence: the report names the date, table, usual time, worst time, and the one-day risk.

The library does not silently delete the 08:00 incident. It lets the operator decide whether that incident should permanently influence the schedule.
