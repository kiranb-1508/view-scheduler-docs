Design spec — impact analysis

Who Uses This

Given a table or view, what breaks if you change it. A separate tool from the scheduler, for a reason worth understanding before you build either.

00Why it's separate

The obvious assumption is that impact analysis is the scheduler's dependency walk run backwards. It isn't, and the difference decides the architecture.

view_dependencies has no reverse index. The UC Tables API answers "what does this view read" for one object. Nothing answers "what reads this table" — to get that from declared metadata you would have to fetch every view in the metastore and invert the result. That is a full-catalog crawl to answer one question.

So impact analysis uses a different source entirely: system.access.table_lineage, which is observed rather than declared, and queryable in both directions with plain SQL.

That last point is a genuine gain, not a consolation. Declared metadata knows about views and tables. Observed lineage also captures dashboards, DBSQL queries, notebooks, jobs and pipelines — which is where the business impact of a change actually lands.

01The whole tool

One SQL query, one recursion, one report. Considerably smaller than the scheduler.

Hops matter more than raw count. A dashboard three hops away still breaks; a table nobody has read in two months probably doesn't need a migration plan. Both facts are on screen without anyone computing a score.

02The query

Recursive CTE, available on DBR 17.0+ and DBSQL 2025.25+. The depth cap and the seen guard are not optional — job-level cycles exist even though view-level ones cannot.

WITH RECURSIVE edges AS (
  SELECT DISTINCT
      source_table_full_name AS src,
      target_table_full_name AS tgt,
      entity_type,
      MAX(event_time) AS last_seen
  FROM system.access.table_lineage
  WHERE event_date >= current_date() - INTERVAL 90 DAYS
    AND source_table_full_name IS NOT NULL
  GROUP BY 1,2,3
),
up AS (
  SELECT tgt AS node, entity_type, 1 AS hops, last_seen
  FROM edges WHERE src = :target

  UNION ALL

  SELECT e.tgt, e.entity_type, up.hops + 1, e.last_seen
  FROM edges e
  JOIN up ON e.src = up.node
  WHERE up.hops < 6
)
SELECT node, entity_type, MIN(hops) AS hops, MAX(last_seen) AS last_seen
FROM up GROUP BY node, entity_type
ORDER BY hops, last_seen DESC
Two things that will bite

Partition filter first. system.access.table_lineage is partitioned on event_date. Without that predicate the query scans a year of account-wide lineage.

Cap the depth. Six hops is already more than anyone acts on, and a wide graph without a cap will run away. If your workspace predates recursive CTE support, run the same thing as a Python loop — six iterations of a simple join, same result.

03Two honest limits

It only sees what ran. Lineage is emitted when a workload executes. A quarterly report that hasn't run since June will not appear, and you will not be told it's missing. This is the mirror image of the scheduler's constraint — there, declared metadata was the right source precisely because a new view has never run.

It stops at the catalog boundary. Tableau, Power BI, Excel extracts and reverse-ETL syncs are invisible to Unity Catalog. If those matter, keep a small hand-maintained list of external consumers per critical table. Twenty lines of YAML beats a dashboard that quietly under-reports the thing people care about most.

The free supplement

If the scheduler caches the dependency graphs it walks, invert that cache and union it in. It covers exactly the gap above — declared dependencies that haven't run yet — for no extra cost, since the scheduler computed them anyway. Add it once the scheduler is in use, not before.

04Config and build order

Two parameters: window_days (90) and max_hops (6).

  1. Run the query by hand against a table you already understand. Check the direct consumers match what you know before trusting anything transitive.
  2. Wrap it, add the hop grouping and the stale-consumer warning.
  3. Stop. Column-level impact, blast-radius scoring and owner lookup are all real features and none of them are needed to answer the question in the title.
Shared with the scheduler

A config module and output formatting. That's the honest extent of it — worth a small common package, not worth merging the tools.
