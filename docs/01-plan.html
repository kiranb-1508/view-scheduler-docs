The Lazy Scheduler

Same problem, roughly a fifth of the machinery. Show the data, recommend the obvious number, and make being wrong cost a wait instead of bad numbers.

What went wrong with v3

Almost every complicated part existed to make a judgment automatically that a human makes instantly by looking.

A classifier deciding whether a table is weekly. A slot model deciding which of three daily refreshes counts. Changepoint detection noticing a schedule moved. Every one of those is a machine straining to reach a conclusion that is obvious the moment you put the last 30 days on screen.

So: stop deciding for the user. Show them the thirty days and let them see it.

No confidence tiers, no coverage percentages, no vocabulary anyone has to learn. "Worst day in 30" and "worst but one" are the same two order statistics from v3 — just said in words a person already knows.

The weekly table isn't a classifier output buried in a report. It's a row saying Mondays, which anyone reads in half a second.

The gate — 15 lines that replace most of the spec

Drop this at the top of the materialization job. It checks instead of predicting.

def wait_for_deps(tables, timeout_min=90):
    deadline = time.time() + timeout_min * 60
    while True:
        late = [t for t in tables if not refreshed_today(t)]
        if not late:
            return True
        if time.time() > deadline:
            alert(f"skipping: {late} not refreshed")
            return False
        time.sleep(300)

def refreshed_today(t):
    row = spark.sql(f"DESCRIBE HISTORY {t} LIMIT 1").first()
    return row.timestamp.date() == date.today() and wrote_rows(row)
Why this is the real fix

With the gate, a wrong recommendation costs five minutes of waiting. Without it, a wrong recommendation silently publishes yesterday's numbers to a report. That difference is why the gate is worth more than every statistical refinement in v3 combined — and it's shorter than any one of them.

It also deletes the nastiest bug we found: late runs bleeding into the next day and dragging the recommendation earlier. The gate doesn't care what day a commit was attributed to. It asks whether the table refreshed, now.

What you build

  1. Walk the dependencies. Recurse view_dependencies from the UC Tables API. Views pass through, tables are what matter. Unchanged from v3 — this part was never the problem.
  2. Pull each table's history. DESCRIBE HISTORY, keep commits that wrote rows. Read the operation class from operationParameters.mode, not the operation name — plain WRITE is the most common one and its mode is what tells you whether it's a real refresh.
  3. Per table, per day: when did it finish? First qualifying commit of each day. Collect: usual (median), worst (max), days missed, and which weekdays it runs.
  4. Recommend. Worst all-clear across dependencies, plus a buffer. Print the table above.

Four steps. Three config values: days_history (30), buffer_min (15), timezone (IST).

The one thing to keep from v3

Print blind-spot warnings only when they apply to the view in front of you. A foreign table, a permission failure, a function dependency — those get a line each. If none apply, print nothing. The register was right; showing all 18 every run was what made it unreadable.

Honest limits

Two you should say out loud when handing this over, because they're properties of the approach and not bugs to fix later.

  • It proves pipelines finished, not that data is correct. Late-arriving records aren't visible in commit history to anyone, by any method.
  • 30 days is 30 days. "Worst of 30" is a real, useful number, but it is not a guarantee about day 31. The gate is what covers day 31.

The detailed v3 spec stays useful as an appendix — it holds eight rounds of edge cases worth consulting when something behaves oddly. Just don't build from it.
