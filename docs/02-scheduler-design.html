Design spec — analysis path

Scheduler Internals

How the analyzer turns a view name into a schedule time: architecture, code flow, and the four steps that do the work.

00What it does

Input a Unity Catalog view name. Output a recommended daily start time plus the evidence behind it.

It talks to exactly two things: the UC Tables API, to find what the view depends on, and the Delta transaction log via Spark, to find when each dependency last finished. Everything else is arithmetic in memory. No state store, no database, nothing persisted between runs.

01Architecture

The practical consequence of that shape: cost is dominated by step 1, because view_dependencies is one REST call per object and isn't returned by listTables. Step 2 is one Spark call per physical table, which is a smaller number. Memoize the walker on full name and shared subtrees get visited once.

02Code flow

03Step 1 — Walk the dependencies

def walk(fqn, seen=None):
    seen = seen if seen is not None else set()
    if fqn in seen: return [], []          # cycle guard
    seen.add(fqn)

    meta = uc_api(f"tables/{fqn}")          # one call per object
    kind = meta["table_type"]

    if kind == "VIEW":
        tables, skipped = [], []
        for d in meta.get("view_dependencies", {}).get("dependencies", []):
            if "table_full_name" not in d:  # function dependency
                skipped.append((d, "function")); continue
            t, s = walk(d["table_full_name"], seen)
            tables += t; skipped += s
        return tables, skipped

    if kind in ("MANAGED", "EXTERNAL", "MATERIALIZED_VIEW", "STREAMING_TABLE"):
        return [fqn], []

    return [], [(fqn, kind)]                # FOREIGN, HMS, unreadable

Run the calls concurrently with a small pool and back off on 429. A permission error on one node returns it as skipped rather than raising — a partial answer that names its gaps beats no answer.

04Step 2 — Read the history

The one place where detail genuinely matters. Operation class comes from operationParameters, not the operation name. The most common name is plain WRITE, and only its mode says whether it replaced the table or appended to it.

Full replaceWRITE + mode=Overwrite, CREATE/REPLACE TABLE AS SELECT, INSERT OVERWRITEAlways — a recompute that produced zero rows still ran
IncrementalWRITE + mode=Append, MERGE, UPDATE, COPY INTO, STREAMING UPDATEAny row metric > 0. If metrics are missing entirely, qualify and flag the table

def qualifying(row):
    op, p = row.operation, row.operationParameters or {}
    m = row.operationMetrics or {}
    if op in FULL_REPLACE or (op == "WRITE" and p.get("mode") == "Overwrite"):
        return True                              # zero rows still counts
    if op in INCREMENTAL or (op == "WRITE" and p.get("mode") == "Append"):
        if not m: return True                    # degraded — flag the table
        return rows_written(m) > 0
    return False
Test this first

ADF and Synapse Link write through non-Spark paths and may emit sparse or absent operationMetrics. The if not m branch is what stops those tables reading as dormant. Validate it against real tables of each kind before trusting any output — this failure is silent, not loud.

05Steps 3 and 4 — Roll up and recommend

def finish_times(table, days=30):
    hist = spark.sql(f"DESCRIBE HISTORY {table}").collect()
    good = [r for r in hist if qualifying(r) and within(r, days)]
    by_day = {}
    for r in sorted(good, key=lambda r: r.timestamp):
        by_day.setdefault(r.timestamp.date(), r.timestamp)   # first of the day
    return by_day

def recommend(tables, buffer_min=15):
    per_table = {t: finish_times(t) for t in tables}
    days = set.intersection(*(set(v) for v in per_table.values()))
    all_clear = sorted(max(per_table[t][d] for t in tables) for d in days)
    return (all_clear[-1] + buffer_min,        # safe
            all_clear[-2] + buffer_min,        # tighter
            len(days))

Read the intersection carefully. A day only counts if every dependency refreshed on it. Days where something didn't run are excluded from the timing numbers and reported instead in the missed column — because a table that misses days is a reliability problem, and no schedule time fixes it.

Where the two numbers come from

all_clear[-1] and all_clear[-2] are the worst and second-worst days. Those are the same order statistics the earlier spec dressed up as 95% and 99% coverage tiers — with ~21 usable days the maximum is roughly a 95% figure anyway, so the honest presentation is just "worst day in 30" and "worst but one".

Worked example

Two tables, five days. You can't build the view until both have refreshed — so each day, the later of the two is when everything was ready.

Finished atMonTueWedThuFri
orders04:0004:1004:0505:3004:00
customers03:5003:4506:1003:5003:55
all_clear04:0004:1006:1005:3004:00

Wednesday was bad because customers ran late; Thursday because orders did. You wait for the slowest table each day, not the average — the same way you leave when the last friend arrives, not the average friend.

Sort those five all-clear times worst-first: 06:10, 05:30, 04:10, 04:00, 04:00. Then:

  • safe = worst + 15 min = 06:25 — would have worked on all five days.
  • tighter = second-worst + 15 min = 05:45 — 40 minutes earlier, but Wednesday would have failed.

Over 30 days rather than 5, "tighter" fails roughly one day a month. The buffer is only a small margin so the job isn't starting the same second the last table finished.

06Config and output

Three parameters: days_history (30), buffer_min (15), timezone (IST).

Pin the session timezone explicitly. Databricks TIMESTAMP renders in spark.sql.session.timeZone, whose default is UTC — inherit it and the same view returns different clock times on different warehouses. Set it once at the top of the job.

The report carries: the two times, the per-dependency table (refreshes / usual / worst / missed), and warnings only where they apply — a weekly dependency, a table that missed days, a branch that couldn't be read. When none apply, that section prints nothing.

07What to build first

  1. Step 1 against your dummy environment. Confirm the walker terminates and the skipped list is populated correctly for a deliberately unreadable dependency.
  2. Step 2, validated against one table per writer — ADF, Synapse Link, a Databricks job. This is the step that fails quietly.
  3. Steps 3 and 4, which are pure arithmetic and can be unit-tested with a handful of fabricated timestamps rather than real tables.
